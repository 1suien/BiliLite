# 10 · 播放方式对比：0.4.3（WebView 版） vs 0.6.25（原生版）

> 对比对象
> - **A 侧**：本工程还原的 BiliLite 0.4.3 安卓版（Capacitor 6 + Android WebView，官方 APK 4,104,453 B；本工程源码构建产物 4,107,542 B，见 [docs/09](09-生成可安装APK.md)）。A 侧有**原始源码**（`reference/upstream-v0.4.3/`）与本工程源码可逐行对照。
> - **B 侧**：用户附件 `base.apk.1`（3,264,739 B，sha256 `7a9af21c…f853`）——BiliLite **0.6.25** 原生版：`package com.bililite.app`、versionCode **53**、minSdk **24**、targetSdk 35、**单一 classes.dex**（5,731,896 B / 5,795 类）、**无 lib/ 原生库**、**无 web 资源**、Jetpack Compose + Room + OkHttp + **Media3 1.4.1**。B 侧仅有 APK，用 jadx 1.5.1 + dexdump 做静态逆向。

一句话结论：**两版共用同一套 B 站 `playurl` 接口，但取流之后的「播放引擎」完全换了。** 0.4.3 在 WebView 里用自研的 MSE 内核（fetch + `Range` + `sidx`）手工拼 DASH；0.6.25 用 ExoPlayer，把 DASH 分离出来的 video/audio 两条 m4s 直链各包一条 `ProgressiveMediaSource`，再用 `MergingMediaSource` 合并播放。0.6.25 因此拿到系统硬解、前台播放服务、离线缓存、字幕轨道这些能力，代价是必须回到原生工程；0.4.3 的播放全在前端，能跨桌面/安卓复用，但字节级拉流与 MSE 组装全得自己扛。

## 1. 端到端链路

**A：0.4.3（`app/src/`）**

```
路由 /video/:bvid
  └ VideoView.vue  起播时间 startTime()（query.t 或本地学习进度，:766-777）
      └ bili.video.playurl(bvid, cid, qn)        bridge/api.ts:454-520
          └ WBI 签名 GET /x/player/wbi/playurl  fnval=4048 platform=pc
              └ 返回 dash.video[] / dash.audio[] / durl[]
                  └ player/dash.ts 选轨 → MediaSource + SourceBuffer×2
                      └ fetch(Range: bytes=N-) 拉 m4s 分片，按 sidx 定位起播偏移
                          └ <video> 输出（WebView 内 MSE → 平台 MediaCodec）
```

**B：0.6.25（jadx 反编译后）**

```
b3.Db（协程：从状态取 qn）→ Y2.D.q(bvid, cid, qn)       Y2/D.java
  └ 两条 GET 并行：/x/player/playurl?…&fnval=16…（DASH）+ &fnval=0…&platform=html5（mp4 兜底）
      └ 解析 → StreamInfo(videoUrl, audioUrl, qualities, acceptQuality, acceptDesc)
          └ b3.dc.C（最多 4 次、退避 800ms×attempt）
              └ b3.Ua（播放 effect）：url = audioUrl 为空 ? videoUrl : "dash:"+videoUrl+"|"+audioUrl
                  └ b3.dc.N(context, player, url)    组装 MediaSource
                      └ MergingMediaSource(ProgressiveMediaSource(video), ProgressiveMediaSource(audio))
                          └ player.setMediaSource → seekTo(恢复点) → prepare() → play()
                              └ ExoPlayer + MediaCodec 硬解
```

## 2. 取流（playurl）

| 维度 | A：0.4.3 WebView | B：0.6.25 原生 |
|---|---|---|
| 接口 | `https://api.bilibili.com/x/player/wbi/playurl`（`bridge/api.ts:40`） | `https://api.bilibili.com/x/player/playurl`（**不带 wbi 签名**，`Y2/r.java`、`Y2/C0422s.java`） |
| 参数 | `fnval=4048`（DASH+HDR+4K+杜比音频+杜比视界+8K+AV1）、`fnver=0`、`fourk=1`、`platform=pc`、`high_quality=1`、`qn=设置值`（`api.ts:42,454-520`） | DASH 请求：`fnval=16&fnver=0&fourk=1`；html5 兜底：`fnval=0&fnver=0&fourk=1&platform=html5`；qn 均字符串拼接 |
| 请求数 | **1 次** | **2 次并行**（DASH + html5 mp4/durl 两套结果配对使用，`Y2/C0423t.java`） |
| 重试 | Playurl 无重试，失败直接上报播放页 | 协程内**最多 4 次**，间隔 `800ms×attempt`（`b3.dc.C`） |
| 结果模型 | `PlayurlData`：`dash.video[]/audio[]`（url+backup+codecs+mimeType+宽高+带宽）、`durl[]`、`acceptQuality/acceptDescription` | `StreamInfo(videoUrl, audioUrl, qualities, acceptQuality, acceptDesc)`（`Y2/C0407c.java`，toString 证实字段名） |
| 空/错误 | 抛 `Error` → 播放页 `errorText` | 记录 `获取播放地址失败 bvid=… qn=… cid=…` / `接口返回空地址`；UI 文案 `播放出错 code=` |

## 3. 选轨策略

| 维度 | A：0.4.3 | B：0.6.25 |
|---|---|---|
| 视频选轨 | 编码优先级 **avc1 > hev1/hvc1 > av01**，再按分辨率、带宽排序（`player/dash.ts:208-232`） | 先筛 **`codecid==7`（AVC/H.264）** 的第一条，**没有则取数组最后一条**；只取 `baseUrl`（`Y2/D.java` 的 `q`） |
| 音频选轨 | **mp4a 优先**，opus 兜底，再按带宽（`dash.ts:234-241`） | 取 **bandwidth 最大**的一条 |
| 备份线路 | 每条流带 `backupUrl`；把 `*.mcdn.bilivideo.cn` 排到最后再试（`dash.ts:245+`），失败换线 | 播放路径**只用 baseUrl**；`backupUrl` 只出现在离线缓存的下载器 `Y2/V.java` |
| 清晰度菜单 | `accept_quality`/`accept_description` 排序（`views/VideoView.vue:191-198`）；**无「自动」档**；未登录时 ≥1080P 标锁（`:207-211`） | `acceptQuality`/`acceptDesc` 配对（缺则用 `qualities` + `dc.T(qn)` 中文表），去重后**前置 `(0,"自动")`**（`b3.Ua`） |
| 默认 qn | `settings.defaultQuality || 80`（`VideoView.vue:786`） | 状态里上次选择（`AbstractC0661dc.q(state)`） |

> 结果差异：B 侧在「只有 HEVC/AV1 高码率」的视频里可能落到非 AVC 轨道（取最后一条），兼容性/功耗上不如 A 侧的显式编码优先级表；A 侧则因为要兼容 WebView 的 MSE 解码能力，主动把 AVC 排第一。

## 4. 播放装配（核心差异）

### 4.1 A：自研 DASH/MSE 内核（`app/src/player/dash.ts`，1448 行，非第三方库）

- 一个 `MediaSource` + **两个 SourceBuffer**（video/audio 分开 append）。
- **起播优化**：先用 `Range: bytes=0-65535` 探测 MP4 的 `sidx`，算出起始分片字节偏移，再 `Range: bytes=N-` 续拉；`sidx` 不可用时退化为「从 0 顺序拉 + 缓冲到当前位置再跳」（`PROBE_BYTES=65536`）。
- 节奏参数（`dash.ts:116-129`）：`BUFFER_AHEAD=45`(s)、`VIDEO_CHUNK=512KB`、`AUDIO_CHUNK=128KB`、`FLUSH_MS=300`、`FIRST_CHUNK_TIMEOUT/FETCH_TIMEOUT/EVENT_TIMEOUT=8000`。
- 直链 `flv/ts` 动态 `import('mpegts.js')`；其他直链直接给 `<video>`。
- seek 到未缓冲区间 → **重建 MediaSource** 从新位置续流；`QuotaExceeded` → 淘汰旧缓冲。
- 出错自动重连 ≤2 次；分片 403/超时按备份线路重试（0.4.1 的 CDN Referer/UA 修复、0.4.2 的 mcdn 排序 + 8s 首包看门狗就落在这条链路上）。
- 倍速 6 档 `[0.5,0.75,1,1.25,1.5,2]`（`VideoView.vue:145`），写回设置 `playbackRate`（`:456-460`）。

### 4.2 B：Media3 ExoPlayer（`b3/AbstractC0661dc.java` = `b3.dc`）

- **唯一创建点**（`AbstractC0661dc.java:484-512`，jadx 反编译已完整还原）：

```java
Validate.isTrue(1500 >= 0, "bufferForPlaybackMs", "0");
Validate.isTrue(3000 >= 0, "bufferForPlaybackAfterRebufferMs", "0");
Validate.isTrue(20000 >= 1500, "minBufferMs", "bufferForPlaybackMs");
Validate.isTrue(60000 >= 20000, "maxBufferMs", "minBufferMs");
DefaultLoadControl lc = new DefaultLoadControl(new DefaultAllocator(), 20000, 60000, 1500, 3000);
ExoPlayer.Builder(ctx).setLoadControl(lc).build();   // x1/C1957q
player.S(true);        // 布尔开关（形态等同 setHandleAudioBecomingNoisy(true)，未能唯一定名）
// 之后 I()/U()/T() 三个调用设置音频属性与轨道参数（含首选音频语言 zh）
```

- **媒体装配 `b3.dc.N(Context, ExoPlayer, String)`**（`AbstractC0661dc.java:193-239`）：
  - 数据源：`DefaultHttpDataSource.Factory`，**UA = `Mozilla/5.0 (Linux; Android 13) AppleWebKit/537.36 Chrome/122.0 Mobile Safari/537.36`**，显式头 `Referer: https://www.bilibili.com/`；外层 `DefaultDataSource` 以支持 `file://`/`content://`。
  - url 三种形态：
    - `file://` / `content://` → 单条本地媒体；
    - **`dash:<videoUrl>|<audioUrl>`** → 两条 `ProgressiveMediaSource`（MIME `video/mp4` / `audio/mp4`）→ **`MergingMediaSource`** → `player.setMediaSource(...)`；
    - 其他 http(s) 单文件 → 单条 `ProgressiveMediaSource`。
  - 播放：有恢复进度就 `seekTo(pos)` → `prepare()` → 按 `playWhenReady` `play()`。
- **离线缓存播放**走同一入口：`Y2.J.d()` 把缓存的 `.video.m4s`/`.audio.m4s` 拼成 `"dash:"+videoUri+"|"+audioUri`，于是本地缓存也当「两条分离流合并」播（`Y2/J.java`）。

## 7. 为什么两版会这样分叉（根因）

1. **渲染层复用 vs 原生重写**：0.4.3 要和 Electron 桌面版共用同一份 Vue 渲染层 + B 站接口层，播放只能在 WebView 里做；0.6.25 直接放弃复用，用 Compose 重写 UI，于是能上 ExoPlayer。
2. **浏览器没有「把两条 demuxer 流拼起来」的 API**：DASH 分离流在 WebView 里只能自己解析 `sidx`、按字节 Range 拉、手动 append 到两个 SourceBuffer——这就是 0.4.3 那 1448 行内核的由来；原生一行 `MergingMediaSource` 解决。
3. **系统能力决定了功能边界**：前台服务、通知、MediaSession、SAF 目录、锁屏播放都是 Android 系统能力。WebView 侧没有这些封装，所以 0.4.3 只能做「系统 PiP」这一种后台形态；0.6.25 才能做听视频和下载队列。
4. **风控策略不同**：A 侧把 WebView UA 全局改成桌面 Chrome 126（分片 CDN 对 UA 敏感，0.4.1 的修复），并靠 `server.hostname=www.bilibili.com` 让页面同源、自动带上 `Referer`；B 侧在数据源里显式写移动端 Chrome 122 UA + `Referer`，说明 B 站 CDN 对「桌面 UA / 移动 UA + 正确 Referer」两种组合都放行。
5. **接口签名**：B 侧证明 `/x/player/playurl` 不签名也能取流（仅桌面/网页版语境才强制 wbi？）；A 侧与桌面版共用接口层，所以走了 `wbi/playurl` + `w_rid` 签名。

## 8. 各自优劣

**A（0.4.3 WebView）**
- 优：一套前端代码同时跑 Electron 桌面与手机；播放零原生代码，改播放逻辑不用重编 APK。
- 劣：起播与稳定性全靠自研内核（403、mcdn、sidx 缺失、缓冲膨胀、seek 重建都是坑）；无后台播放、无离线缓存；WebView MSE 能解的编码受系统 WebView 限制。

**B（0.6.25 原生）**
- 优：ExoPlayer 成熟的缓冲/重连/硬解；后台播放、通知控制、离线缓存、字幕轨道齐全；Compose 播放页交互（长按倍速、双击跳、截图）更丰富。
- 劣：没有画中画、没有弹幕；每次播放发 2 个 playurl 请求（流量/时延翻倍）；视频只取 `baseUrl` 无备份线路；`codecid==7` 优先在纯 HEVC/AV1 源上可能落到非最优轨。

## 10. 未验证 / 边界

1. **B 侧只有静态逆推，未真机运行**：实际落到哪条清晰度、听视频模式的实现细节、`S(true)`/`T(h0)` 两个调用究竟对应 media3 的哪个 setter（R8 改名后只能按调用形态推断），都未实机验证。
2. **B 侧有 55 处 jadx 反编译失败**（播放页主 effect `b3.Q` 等），本文结论凡涉及这些方法均由 dexdump 指令级交叉核对，未逐条还原成 Java。
3. **A 侧**：无真机日志，起播耗时/缓冲行为见 [docs/09](09-生成可安装APK.md) 的「未验证」一节。
4. **接口行为依赖线上**：`fnval`/`qn` 的可选值、未登录时的清晰度上限会随 B 站策略变化，两版都受影响。
