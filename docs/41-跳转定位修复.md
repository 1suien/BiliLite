# 跳转定位修复（本机 0.4.35）

## 现象（用户录像 2026-11-06）

0.4.34 里点进度条跳转后，画面一直「缓冲中…」，时间停在 `0:00`，等 10 秒以上也不出来。之前 0.4.34 记的调试行 `地址 0.2s · 首块 0.2s · 就绪 0.3s · 可播 0.5s · 播放 0.5s` 说明**正常起播没问题**，问题只出在「跳转到新位置」这条路径上。

## 根因

跳转的实现是「重开 MediaSource，从目标位置继续拉流」。要在 B 站 DASH 单文件里从中间拉，必须先知道目标秒数对应的**字节偏移**，旧代码靠「抓文件头 64KB（不行再抓 512KB）找 sidx 索引」。

但 B 站这种文件的布局是 `ftyp + moov + sidx + mdat`，sidx **不在文件头**，而在 playurl 返回的 `segment_base.index_range` 指定的字节区间里（实测约 929–3852）。于是探测必然失败，代码就退化成「从 0 顺序缓冲，缓冲到目标位置再跳」——目标越远等得越久，看起来就是「卡住」。

## 修法

playurl 每一路轨都带 `segment_base: { initialization, index_range }`：

1. `app/src/bridge/api.ts`：把 `segment_base` 规整进 `PlayUrlVideo/PlayUrlAudio.segmentBase`；
2. `app/src/types.ts`：补 `segmentBase?: { initialization?: string; indexRange?: string }`；
3. `app/src/player/dash.ts`：
   - `probeRanged()` 优先用 `index_range` 精确取 sidx（一次 range 请求），再取 `initialization` 作为 init 段，算出绝对偏移后直接从该偏移续流（206 range）；
   - 没有 `segment_base` 或 range 被 CDN 无视时，才退回原来的「文件头找 sidx → 从 0 顺序缓冲」；
   - 顺序缓冲兜底时状态栏显示「这条线路不支持定位，正在缓冲到 12:34（已缓存 0:45）」，不再无提示；
   - 重建时状态文案用「正在跳转…」而不是「缓冲中…」。

## 验证（对真实 B 站 CDN）

用同一份 playurl 实测（BV1zY4y187cK / P26）：

| 轨 | init 区间 | index 区间 | sidx | 数据段总数 |
| --- | --- | --- | --- | --- |
| 视频 | 0-928（929 B，ftyp+moov） | 929-3852（2924 B） | 241 段，timescale 16000 | 24,643,738 B |
| 音频 | 0-816（817 B） | 817-3740（2924 B） | 241 段，timescale 48000 | 12,932,177 B |

- 目标 30s → 视频偏移 648,383；目标 600s → 12,390,673；音频 30s → 310,307、600s → 6,426,452；
- 按偏移发 `Range: bytes=<偏移>-` 全部返回 **206**，且首块正好是 `moof`（1900 / 1040 B），说明偏移计算正确、可直接续流。

## 限制

- 若某些 CDN 拒绝 Range（极少见），仍会走「从 0 顺序缓冲」兜底，界面上会有进度提示；
- 起点用 `segment_base` 时，如果服务端返回的 `index_range` 缺失（少数老视频），同样走兜底路径。
