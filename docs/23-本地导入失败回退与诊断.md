# 23 本机构建 0.4.16 —— 本地「打开文件」打不开的修复 + 诊断

> 这是接在 0.4.15（本地视频改原生导入 + WPS 分享接收）后面的**真机问题修复**。
> 0.4.15 把安卓的「打开文件」改成了原生 SAF 导入（`LocalMediaPlugin`），结果真机上点「打开文件」没反应，
> 同一台机器点「打开文件夹」（走 WebView `<input type=file>`）却是好的。

## 1. 用户报告

m03599 截图（「本地」页，0.4.15 的新文案已经生效）＋ 原话：

> 「文件打不开，文件夹能打开」

也就是同一个页面上两个按钮：

| 按钮 | 0.4.15 走的路径 | 真机表现 |
|---|---|---|
| 打开文件夹 | `local:pickFolder` → WebView `<input type=file multiple>` | ✅ 正常 |
| 打开文件 | `local:pickFiles` → 安卓走 `local.pickNative()` → `LocalMediaPlugin.pickAndImport`（`ACTION_OPEN_DOCUMENT`） | ❌ 点了没反应 |

## 2. 定位

两件事互相印证：

1. **`<input type=file>` 这条路是通的**——「打开文件夹」用的就是同一个 `pickFilesWithInput({ accept: 'video/*,audio/*', multiple: true })`；
2. **坏的是原生插件这条路**。`LocalMediaPlugin.pickAndImport` 用 `ACTION_OPEN_DOCUMENT` + `EXTRA_MIME_TYPES`，
   如果这台平板 ROM 把「文档选择器（DocumentsUI）」裁掉/禁用了，`resolveActivity` 找不到处理者，
   `startActivityForResult` 直接抛异常或返回错误；而 JS 侧 `pickFiles()` 里只 `ui.err(e.message)` 闪一下 toast，
   用户很可能什么都没看到，表现就成了「点了没反应」。

顺带确认了几个不是原因的东西：

- 插件本身编译进去了（`classes*.dex` 里有 `LocalMediaPlugin`），`MainActivity` 也在 `super.onCreate()` **之前**注册（Capacitor 6 的 `registerPlugin` 是往 `bridgeBuilder` 里塞，必须在 `super.onCreate` 前）；
- Capacitor 的 `@ActivityCallback` 私有方法是可用的（`Plugin.initializeActivityLaunchers()` 用 `method.setAccessible(true)`）；
- 0.4.14 里这个按钮（当时走 `<input>`）也失败过，说明这条路在某些 ROM 上确实不稳，**不能只依赖原生，也不能只依赖 input**。

## 3. 改动（0.4.16）

### 3.1 原生插件兜底（`app/android/app/src/main/java/com/bililite/app/LocalMediaPlugin.java`）

- 新增 `buildPickIntent(action, multiple)` 与 `canHandle(intent)`（`intent.resolveActivity(packageManager) != null`）；
- `pickAndImport`：先 `ACTION_OPEN_DOCUMENT`，不可用就退到 **`ACTION_GET_CONTENT`**（老式选择器，几乎每家 ROM 都有）；
- 两者都不可用 → `call.reject("这台设备上没有可用的系统文件选择器…")`，让 JS 回退；
- `startActivityForResult` 包 `try/catch`，异常也变成可读的 reject；
- 新增 `@PluginMethod diagnose()` → `{ openDocument, getContent, sdk, mediaDir }`，用来回答「系统选择器到底有没有」。

### 3.2 JS 侧失败回退 + 可见的诊断（`app/src/views/LocalView.vue`）

`pickFiles()` 现在的顺序：

1. 安卓且插件可用 → `bili.local.pickNative()`，并用 `Promise.race` 加 **9 秒看门狗**：
   - 9 秒还没回 → 不算失败，页面上提示「原生选择器 9 秒没反应」，并出现「改用系统文件选择器」按钮（不自动开第二个面板，避免两个选择器打架）；
2. 原生抛错 → 记下原因（`nativeError`）、`console.warn`，**自动回退**到 `bili.local.pickFiles()`（WebView input）；
3. 回退也失败 → toast 报错。

页面上（只在 Android 显示）多了一行：

```
原生导入：选中的文件会复制到 App 私有目录，刷新/重启后还在   [检测]
```

- 点「检测」→ 调 `diagnose()`，显示「系统文档选择器：可用 / 不可用 · 备用选择器：可用 / 不可用 · Android SDK 版本」；
- 原生失败后这一行变红：「原生导入失败：<原因>（已回退系统文件选择器）」，并出现「改用系统文件选择器」按钮；
- 任何一个都失败/不可用时，用户都能截图把这行发回来，定位不用靠猜。

### 3.3 桥层

- `app/src/bridge/android.ts`：新增通道 `'local:diagnose'`，`bili.local.diagnose()`；
- `app/src/bridge/types.ts`：`local.diagnose?(): Promise<any>`；
- `app/src/bridge/index.ts`：延迟代理透传（没有原生诊断时返回 `{ openDocument: false, getContent: false, sdk: 0 }`）；
- `app/src/bridge/mock.ts`：mock 实现（浏览器预览里明确显示不可用）。

## 6. 升级 / 使用

- 与 0.4.15 同签名，**直接覆盖安装**即可（保留数据）。
- 装完到「设置 → 关于」确认 `v0.4.16`。
- 本地 → 点「检测」，会显示这台平板的系统文档选择器可不可用：
  - 如果显示「可用」但「打开文件」还是没反应，说明是插件调用别的问题 → 把这行文字截图发回来；
  - 如果显示「不可用」，点「打开文件」会自动退到系统文件选择器（`<input>`，和「打开文件夹」同一条路），
    这时文件只能临时登记（刷新后失效），要持久保存请等下一步适配。
- WPS 分享接收不受影响（`ACTION_SEND` / `ACTION_VIEW` 走的是分享面板，不是文档选择器）。

## 7. 未验证 / 限制

- 真机上的 SAF 选择器与 `ACTION_GET_CONTENT` 兜底没实测（本机没有连接平板）；
- 回退到 `<input type=file>` 时，导入的文件仍是内存 blob（刷新失效、大文件吃内存），这是 0.4.14 及以前的行为；
- 部分 ROM 的「文件管理」会把 `ACTION_GET_CONTENT` 也接管，行为要实测；
- 9 秒看门狗只是兜底提示，不会取消已经发出的原生调用（用户取消后不会再弹）。
