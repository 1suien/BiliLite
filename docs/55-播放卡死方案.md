# 播放卡在「缓冲中…」的修复方案（待确认，未写代码）

## 现象（用户录像 2026-11-08）

视频《终于弹了这首 世界上最治愈的钢琴曲♪卡农》BV1L4411U7Fj P1（5:28，1080P）点开后：

- 画面一直「缓冲中…」，30 秒不动，时间停在 0:00；
- 调试行：`地址 0.3s · 首块 0.2s · append 2次/0.0s · 0.0MB · 0.0MB/s`
  - `地址 0.3s`：播放地址拿到了；
  - `append 2次`：视频 init 段 + 音频 init 段各 append 了一次；
  - `0.0MB`：之后**一个媒体字节都没再来**；
  - 没有错误卡片 → 说明是「请求挂着不返回」而不是「请求失败」。

## 根因判断

现有 `app/src/player/dash.ts` 拉流循环里只有一个「首包超时」（`FIRST_CHUNK_TIMEOUT = 8s`），而且**首字节一到就清掉定时器**。所以：

1. CDN 返回响应头、发完 init 段之后不发数据（B 站部分 CDN/镜像节点偶发）→ `reader.read()` 永远挂着；
2. 没有任何「空闲超时」把这条线路判死，也没人去换备用线路；
3. 因为没抛异常，0.4.33 加的「CDN 错误自动换线路」也不会触发；
4. 调试行里 host 也没打出来（取 host 的代码在 fetch 返回后，此路径下没走到 / 或者被跳过），现场信息不足。

## 方案（P0 + P1 一起做，1 次出包）

### P0 拉流空闲看门狗（核心）

在 `streamFrom()` 读循环里加：

- 记录 `lastByteAt`：每次 `reader.read()` 拿到数据就更新；
- 每 1s 检查一次：`Date.now() - lastByteAt > IDLE_TIMEOUT`（默认 **6s**）→
  - `abort.abort()` 掉当前线路；
  - 打日志「线路 X 6 秒没有数据，换线路」；
  - 换下一条备用 URL（`withBackups` 已经给了 lz 主 + 备用）；
- 所有备用线路都空闲超时 → 重新调用一次 `videoPlayurl()` 拿新地址再试（限 1 次）；
- 仍然失败 → 显示错误卡片「这条视频的线路都拉不动」，卡片上的「重新获取播放地址」可用于手动重试。

同时把「首包超时」改成「首包 / 首个有效数据」双计时，避免 init 段一到就把定时器清掉。

### P0 调试行补全

`updatePerf()` 增加：当前线路 host（先写进 stat 再显示）、`拉流 n 次`、`等待数据 x.xs`、已下载字节；卡住时能直接看出是哪一跳的问题。

### P1 用户可感知的兜底

- 卡住 6s 自动换线路时，状态栏显示「这条线路拉不动，正在换线路…」；
- 换线路失败后，在错误卡片上多给一个「换 720P 试试」按钮（重新用 720P 取一次 playurl）；
- 连续两次失败后不再自动重试，避免一直转圈。

| 文件 | 改动 |

## 验收

1. 模拟「响应头 + init 段后不再发数据」：用 mock 拦截 fetch 让 body 挂起 → 6s 内自动换到下一条线路并起播；
2. 正常视频起播/跳转不回归（课表回归 + 评论回归脚本跑一遍）；
3. 真机：用户那条卡农视频能起播；调试行能看到 host 和「拉流 N 次」。
